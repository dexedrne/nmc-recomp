# Xion’s look, Roxas’s moves

**Yes. Rebind the unhooded Xion mesh from `obj/N_PO010_BTL.mdlx` to the exact skeleton in each NMC player model.** Start with `obj/P_EX100.mdlx`. Generate a replacement containing the recipient’s bone records, collision and behavior script, and the donor’s painted geometry and textures. The existing motions then address the same joints, including both weapon sockets. This is feasible from the measured formats. A working exporter, a posed round-trip and in-game parity are still unverified. No model or game modification was built.

The ally is the best face donor. Its embedded materials include black hair, blue eyes and a mouth. Rescue Xion, `P_EX220`, is a hooded alternative. The 203-bone `P_EX220_RTN` is **Mickey**. The most important scope decision is to cover forms and alternate playable Roxas slots. The PC member table selects **15 distinct gameplay model paths across four bind tables**. Replacing only the default model would visibly revert during ordinary play, including the early BTLF sequence. Offsets are little-endian. For type 4, let H = member offset + 0x90. H+0x10 gives the count and H+0x14 points from H to 0x40-byte bone records. The OpenKH schema uses signed 16-bit parent at record+4 and child at +6. Reading +4 as signed 32-bit happens to work on the examined hierarchy values. Local S/R/T vectors start at +0x10/+0x20/+0x30. Absolute positions use scale, X/Y/Z rotations and translation followed by parent composition. Comparison tolerances are 0.0001 per local SRT component and 0.001 game units per world coordinate. ## 3. Recommended pipeline

1. **Freeze the recipient interfaces.** Record BAR types, names, link indices, bone/part tables, group visibility IDs, bounds, shadow, BDX, collision and MSET hashes for each target. Base has type 4 `srko` at 0x50, type 7 `tim_` at 0x37540, type 23 collision at 0x7ac00, type 3 `m_ex` at 0x7af60. Use the target BAR as the shell. First demonstrate an unedited model read/write/read with identical semantics and unchanged gameplay members. [BAR inventory](/home/user/work/khnmc-build/out/model-bar.tsv)
2. **Decode both models into a common rest space.** PC loose MDLX retains the PS2-style entity DMA/VIF layout. Read the 0x20-byte group headers at H+0x20, the VIF streams, 16-byte DMA tags, their QWC/address, and packet-local matrix lists separated by −1. Interpret VIF UNPACK into VU memory, then the vertex ranges, weighted-position mixes, strip flags, UVs and optional colors/normals. Rigid points have implicit unit weight. Blended XYZ is already multiplied by W in each bone’s local space. Sum transformed contributions. Example: base’s first VIF packet at 0x3bc0 is 85 quadwords. Rescue’s first at 0x1200 is 57 and its tag is at 0x4910. [Packet measurements](/home/user/work/khnmc-build/out/packet-texture-audit.json) · [Decoder and class references](/home/user/work/khnmc-build/out/toolchain.md)
3. **Bind the recognizable ally in Blender.** Use a reversible axis/unit conversion and stable integer joint IDs. Align hips, knees, shoulders, jaw and both palms to each recipient’s actual rest pose. Donor 28→29 carries head/face regions, while donor 10 and 35 branch into the fingers. Use the recipient’s existing weights as regional transfer guides, inspect vertex groups in poses, then paint folds, wrists, fingers, hair and face layers. Keep target sockets rigidly defined. Remove or hide any donor prop only after identifying its geometry. A hooded look can instead use the two-image rescue donor. [World-space landmarks](/home/user/work/khnmc-build/out/bones.tsv) · [Draw groups](/home/user/work/khnmc-build/out/mesh-groups.tsv)
4. **Write KH2-native data.** For each influence store weight × inverse-bind-transformed position, rebuild palettes, split oversize packets, regenerate VIF/DMA references, strip winding, material/part flags and aligned offsets. Handle or regenerate the shadow on the recipient rig. Preserve the recipient part references and gameplay skeleton, including undeformed joints. Check visual bounds separately from gameplay collision. Copy or adapt donor `tim_`, then rebuild the BAR directory and validate every range. With OpenKH, inspect `OpenKh.Kh2/Models/ModelSkeletal.cs`, `ModelCommon.cs`, `Models/VIF/VifProcessor.cs`, `OpenKh.AssimpUtils/Kh2MdlxAssimp.cs`, and the KH2 MDLX editor’s `Views/Main2_Window.xaml.cs` and `Utils/MdlxEditorImporter.cs::replaceMeshModelSkeletal`. Its Assimp path uses bone ordinals, so FBX dropping unused joints is an explicit validation case. The checkout is sparse. The supplied Windows editor needs .NET 8 Windows Desktop, and no working native editor/runtime was verified here. Use Python plus headless Blender 5.2.3 with the OpenKH algorithms, or an already working owner-side editor. No install is needed for this study. [Writer, reader, FBX/DAE and local source details](/home/user/work/khnmc-build/out/toolchain.md)
5. **Bind textures and the face.** Type 7 is KH2 ModelTexture/RAW, distinct from standalone type-10 TIM2. Respect GS TEX0/CLUT addressing, transfer format, swizzle, PS2 alpha and TEXA patch layout. Preserve donor UVs and materials. Base has three GS images and three TEXA blocks at 0x5b908, 0x700f8, 0x76b58. Both battle donors have zero TEXA. Enable a neutral face for the proof, then author matching eye/mouth rectangles, sheets, animation IDs and frames where the target calls for them. Test blinking independently of scene lip sync. PC pairs HD art to the loaded model’s original-asset offsets. NMC ships exactly `remastered/obj/P_EX100.mdlx/-0.png` through `-5.png`, and **zero** model HD files for P_EX220. Its six baked DDS are vanilla Mickey entries, none matching the loaded model’s two offsets. For the baseline select embedded art with an explicitly empty per-model HD table. [GS/TEXA order and sizes](/home/user/work/khnmc-build/out/toolchain.md) · [Exact shipped and baked paths](/home/user/work/khnmc-build/out/hd-inventory.tsv)
6. **Build each appearance binding.** Reuse a validated bind only when the complete bone records match. Generate each target from its own shell. Derive HUD/shop images from the owner’s ally for an unhooded result. Keep battle voice as an independent presentation choice. Assemble the logical manifest below and resolve it at startup. [Target list and origin of every proposed appearance file](/home/user/work/khnmc-build/out/appearance-overlay.tsv)
7. **Prove parity through normal entry points.** Reparse the product independently. Hash the recipient skeleton, BDX, collision and all original motions/triggers. Compare rest and posed vertices, actual hand/socket transforms, and baseline gameplay traces on identical input. Exercise ground/air chains, magic, each available Drive and transition, dual wield, reaction commands, limits, damage/recovery, HUD states and a low/high-poly event. Compare hit frames, damage, timing, root displacement and effects against stock NMC. Smoke-test loose and HD reads on Linux, Apple desktop and iPhone, then restart with the switch absent and compare against baseline. These are acceptance tests for a future build.

## 4. Forms, weapons, voices, HUD and scenes

**Forms and weapons.** `MAGF` is Bladeless, `KH1F` Light & Dark, and `ULTF` Awakened. Base and MAGF share one complete 229-bone table. BTLF, KH1F and ULTF use a second 229 table with 19 different local SRTs from base despite identical parent IDs. KH1F and BTLF have a `p_ex` member. Stock TRIF/HTLF use 228, and conditional `P_EX110_BTLF` uses vanilla Roxas’s distinct 229. The recommendation is a Xion version for each selected form, preserving its visual cues and mechanics. Object 84’s `00objentry.bin` row at 0x13e8 has weapon selector 1 at +7. `03system.bin/sklt` entry at 0x175fc gives joints **178 and 86**. Retain separate `W_EX*` models, equipment IDs and both attachments. Test off-hand trails and floating-weapon effects. [Destination hashes](/home/user/work/khnmc-build/out/appearance-models.tsv) · [Weapon and form evidence](/home/user/work/khnmc-build/out/visibility.md)

**Battle voice is optional, and a byte-for-byte bank rename loses cues.** The three source paths are individual extensionless SCD **files**, `remastered/obj/{P_EX220,N_PO010_BTL,N_PO010_RTN}.a.us/voice/battle/us/xion`. Each is 172,112 B and SHA-256 starts `d372848a`. The respective type-34 members are `mick` at 0x173920, `xion` at 0x900b0 and `mick` at 0x900b0, all with the `ORIGIN` path at member+0x10. Base `P_EX100.a.us` has no such member. It uses world player banks. NMC ships 16 identical 224,240-B banks (representative `tt0_sora` SHA-256 prefix `3d28d444`). These PC SCD IDs should be evaluated independently of the PS2 VSB counts in DATA-REPORT.

| Measured SCD | Counts at 0x30 (sound / track / audio) | Local sound IDs having a track |
|---|---:|---|
| NMC world player | 34 / 32 / 32 | 1–3, 5–33. IDs 0 and 4 have zero tracks. |
| Xion | 38 / 20 / 20 | 0, 2, 8–11, 13–16, 21–23, 29, 31–35, 37. The rest have zero tracks. |

Sound-offset arrays start at 0x50. For these normal one-track entries, record+0x0c is the local sound number and +0x10/+0x12 are track/audio indices. For example player sound 1 at 0x1390 selects track 0 and audio 29. Xion local sound 1 has no track. Audio stream ordinal alone is insufficient. `00battle.bin/vtbl` at 0x24ba9 contains 241 rows of 14 bytes after its 8-byte header. Character 1 action 0 selects VsbIndex 6 or 5, action 4 selects 9–13, action 9 selects 1/2, action 15 selects 1, and actions 24/27 can request 35 or 34/35. PC EXE RVA 0x3cdb60 selects the signed index/weight and handles −3 specially. At 0x3d5208–16 a nonnegative selection goes to the play helper. The US world-bank name format is used at 0x3cdf5e. The final indexing convention for every caller, the behavior for 34/35 against this world bank, and utterance equivalence are **unverified**. [Sound and track definitions](https://github.com/NotAdam/Lumina/blob/master/src/Lumina/Data/Parsing/Scd/ScdSound.cs) · [Local Vtbl schema](</home/user/projects/kh2-nmc-analysis/scratch/okh/Battle_Vtbl.cs>)

For a voice edition, audition locally and trace action → requested VSB ID → bank/local sound → audio. Rebuild each **recipient** cue table with those same IDs, priorities, routing and empty entries, selecting or reusing an appropriate Xion clip for each audible cue. Reuse the same generated bank at the 16 world keys. Check the forms’ separate `taun` banks and direct script/motion-trigger voices independently. Default to NMC audio until the cue map passes. No new dialogue recording is required for a look-only edition. ## 5. Exact switch and overlay scope

Proposed iPhone `khnmc.conf` line: `env KHNMC_PLAYER_LOOK=xion`. Desktop launchers can set the same environment variable. Select the profile before resource caching. Route size queries, reads and stream opens through the same resolver, retain the original logical key at resource registration, and supply matching per-key HD metadata. The inspected port has separate loose lookup and HD-table construction. A directory of renamed PNGs on its own cannot override both. Preserve other HD slots of partially edited APDX files. [Resolver and config source references](/home/user/work/khnmc-build/out/visibility.md)

* **Body baseline, 15 generated MDLX.** Under `obj/`, append `.mdlx` to each stem: `P_EX100`, `P_EX100_BTLF`, `P_EX100_MAGF`, `P_EX100_KH1F`, `P_EX100_TRIF`, `P_EX100_ULTF`, `P_EX100_HTLF`, `P_EX101`, `P_EX101_BTLF`, `P_EX110_BTLF`, `P_EX121`, `P_EX100_WI`, `P_EX100_WI_MAGF`, `P_EX100_WI_KH1F`, `P_EX100_WI_ULTF`. Each bundles the owner’s target shell and donor-derived geometry/RAW. Use an empty HD table for each body in the embedded baseline. For the seven-image ally RAW, an HD edition can generate `remastered/obj/<stem>.mdlx/-0.png` through `-6.png` for each stem, recalculating the order/count if TEXA is added. No gameplay MSET, collision replacement, BDX transplant, object-table, magic, weapon or AI override is required. [Member selectors](/home/user/work/khnmc-build/out/pc-memt.tsv)
* **HUD/shop, optional presentation files.** The [51-row appearance manifest](/home/user/work/khnmc-build/out/appearance-overlay.tsv) enumerates the above 15 models, 15 generated `obj/<stem>.a.us` fallbacks, 15 exact per-actor DDS replacements, and six shop files. The three shop stems are `p_ex100`, `p_ex101`, `p_ex100_wi`, each with generated `menu/shopface/<stem>.bin` and `remastered/menu/shopface/<stem>.bin/-0.dds`. Body art, generated unhooded HUD and shop art can all originate from owner data. The hooded HUD alternative copies the owner’s rescue DDS under the destination ordinal.
* **English voice edition only.** Generate `voice/us/battle/<world>0_sora.win32.scd` for `al bb ca dc eh hb he lk lm mu nm po tr tt wi`, plus `voice/us/battle/tt0_roxas.win32.scd`. The eight form-specific companion keys under `remastered/obj/<stem>.a.us/voice/battle/us/<bank>` are `P_EX100_BTLF/lnd`, `P_EX100_KH1F/lnd`, `P_EX100_MAGF/bladeless`, `P_EX100_ULTF/awakened`, `P_EX100_WI_KH1F/lnd`, `P_EX100_WI_MAGF/bladeless`, `P_EX100_WI_ULTF/awakened`, `P_EX101_BTLF/lnd` (stem/bank pairs). Generate against each target bank’s own routing and only enable verified cue mappings. The three original Xion banks are read-only donor inputs. Story audio is separate.

**Owner inputs and open gates.** The owner’s loaded NMC data already supplies both meshes, textures, player shells, animations, HUD references and battle recordings. I selected the unhooded ally, embedded body art and existing battle voice as the baseline. Alternate costumes, bespoke HD art, a particular voice performance and broader cutscene coverage are optional artistic choices. A third-party donor would need a locally available revision for bone comparison and suitable terms for the intended distribution. The engineering gates are a lossless control round-trip, acceptable coat/face/grip deformation, and parity tests on the actual port. Until those pass this is a feasibility result, not a tested player option.
